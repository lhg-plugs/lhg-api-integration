# lhg-api-ship：联调自检与上线门禁

> 目标：把「对接完了」变成可验证的结论，而不是「我觉得调通了」。
> 核心纪律：**先跑脚本（机器），再做联调（人）；blocker 不清零，不许说对接完了。**

## 1. 何时使用

- 封装代码写完，准备调真实接口 → 全流程
- 对接代码要提交/上线 → 全流程 + 第 5 节上线检查
- 只想快速看一眼代码有没有硬伤 → 只跑第 2 步脚本

## 2. 第一步：跑确定性审计脚本（必做，零成本）

在项目根目录执行插件自带的审计脚本（用你所在平台执行本地脚本的方式）：

```
python3 <插件目录>/scripts/audit/api_audit.py --target <对接代码目录>
```

- 脚本含 18 条规则：密钥硬编码、密钥进日志、明文 HTTP、无超时、无重试、无限重试、429 未处理、无分页、分页无终止、空异常吞没、错误码不分级等。
- 有 blocker 时脚本以非零 exit code 退出 —— 这是设计，不是 bug。
- `--fail-on` 控制 exit code 语义：默认 `blocker`；想要更严可设为 `warning`。
- 脚本自动跳过 `node_modules/.git/__pycache__/fixtures` 等目录。

## 3. 第二步：分级与修复

| 级别 | 定义 | 处理 |
|---|---|---|
| blocker | 上线后会出事：密钥硬编码、无超时、无限重试、空异常吞没、关闭证书校验 | 必须修，不修不许提交（commit 前的 hook 会拦截） |
| warning | 大概率是坑：无重试、无 429 处理、无分页、错误不分级、密钥放 URL 参数 | 本次修掉；修不掉写理由+有效期进报告 |
| nit | 洁癖项：函数缺文档、URL 字面量散落 | 顺手修 |

分级是死的，判断是活的：如果某条 warning 在你的场景里就是会出事，把它升成 blocker，并在报告里写清理由。

修复顺序：安全类（密钥/证书）→ 健壮性（超时/重试）→ 正确性（分页/错误处理）→ 可维护性。

**修不掉的 blocker**（如需要用户提供真实密钥）：列进报告「需人工处理」区，**不许**为清零改规则或阈值 —— 那是作弊。

## 4. 第三步：真实联调（按顺序，一步一验证）

1. **鉴权先行**：先调最简单的读接口（如 `GET /me` / `GET /status`），确认 401/403 排查清单（见 lhg-api-auth 第 6 节）走完、能拿到 200。
2. **读接口**：调 2-3 个核心读接口，核对返回字段跟文档对得上（字段名、分页形状、空数据长什么样）。
3. **分页实测**：用 `iter_all_*` 拉两页，确认终止条件生效（不会死循环拉到天荒地老）。
4. **写接口**：先在沙箱/测试环境调，确认幂等（同样的请求发两次，不会创建两条数据；或文档说明了如何处理重复）。
5. **错误实测**：故意传错一个参数，看错误翻译是否人话、调用方能否看懂。
6. **限流实测**：按策略卡的频率跑 1 分钟，确认无 429；或故意触发一次 429，确认退避生效。

**联调记录表**（每个接口一行，存进 `API_DOCK.md`）：

| 接口 | 状态 | 备注 |
|---|---|---|
| GET /me | ✅ 200 | 鉴权通过 |
| GET /items | ✅ 200 | 分页 page/per_page 生效 |
| POST /orders | ⚠️ 沙箱通过 | 生产环境待用户确认后调 |

## 5. 第四步：上线检查清单

- [ ] 生产 key 已申请（跟测试 key 分开），环境变量已配置
- [ ] 测试 key 已 revoke 或确认不会再用
- [ ] 重试/限流策略按生产配额复核过（测试环境的配额可能更宽松）
- [ ] 日志里不打完整请求体（可能含用户敏感信息），错误日志脱敏
- [ ] 熔断告警通道已验证（手动触发一次，看告警能不能收到）
- [ ] 回滚方案：如果新对接出问题，能切回老逻辑吗？key 能立刻 revoke 吗？

## 6. 自查报告模板

```markdown
# API 对接自查报告（YYYY-MM-DD）
- API：<名称> / Base URL：<...>
- 审计：blocker=X warning=Y nit=Z（脚本输出附后）
- blocker 处理：<逐条说明修了 / 列入需人工处理>
- warning 豁免：<理由 + 有效期>
- 联调记录：见 API_DOCK.md 联调记录表
- 需人工处理：<如生产 key 申请、生产环境写接口验证>
- 结论：通过 / 不通过
```

## 7. 反模式（不要这么干）

- ❌ 没跑脚本就说「调通了」—— 机器 5 秒能抓的硬伤，别用人眼赌
- ❌ 直接在生产环境调写接口 —— 先沙箱，幂等确认了再上生产
- ❌ 联调记录只写「OK」—— 出问题时回查，OK 是最没用的记录
- ❌ 测试 key 和生产 key 混用 —— 泄露时一起完蛋
- ❌ 为清零改脚本规则 —— 作弊，不是自查

## 7. 联调常见报错速查表

| 报错 | 大概率原因 | 先查什么 |
|---|---|---|
| 401 Unauthorized | 凭证错/过期/没带 | lhg-api-auth 第 6 节六步 |
| 403 Forbidden | 凭证对但权限不够 | scope/套餐/ IP 白名单 |
| 404 Not Found | 路径拼错/版本号错 | base_url 末尾斜杠、v1/v2 |
| 400 Bad Request | 参数缺/类型错 | 必填校验、参数名大小写 |
| 429 Too Many Requests | 触发限流 | Retry-After、降低频率 |
| 500/502/503 | 对方服务抖动 | 等+退避重试，别反复打 |
| SSL 错误 | 证书/verify 问题 | 系统时间、代理配置（绝不用 verify=False 糊弄） |
| 连接超时 | 网络/对方挂了 | 先 curl 试连，再查 DNS/代理 |

## 8. 误报处理

规则是启发式，一定会误伤。误报不可怕，乱处理才可怕：

1. **判断三问**：这行代码真的有问题吗？这条规则的本意是什么？按规则改了会不会破坏功能？
2. **确认误报**：在代码处加一行注释说明原因（如 `# 演示用占位 key，上线前替换 -- 豁免 API-SEC-001`），并记入报告的豁免清单。
3. **拿不准**：按 warning 处理，不要直接忽略。
4. **规则本身有问题**：附最小复现代码提 issue（见第 10 节），说明「期望行为」，不要自己改脚本阈值。

## 9. 审计频率与回归

- **每次改完对接代码**：只跑脚本（5 秒），blocker 当场修。
- **每次提交**：hook 自动跑，有 blocker 会被拦截。
- **上线前**：跑本 skill 全流程（含真实联调六步）。
- **API 文档更新时**：重跑鉴权卡片 + 接口清单，diff 出变化点。

## 9. 多环境 key 管理速查

| 环境 | key 来源 | 放哪里 | 注意 |
|---|---|---|---|
| 本地联调 | 测试 key（控制台申请） | 本地 `.env` | 绝不提交 git |
| CI/测试 | 测试 key（单独申请） | CI 的 secrets | 跟本地 key 分开 |
| 生产 | 生产 key（单独申请） | 服务器环境变量/密钥管理服务 | 申请后第一时间验证连通性 |

**三条铁律**：
1. 测试 key 和生产 key 永远分开申请 —— 混用等于把生产钥匙发给所有人。
2. key 只进环境变量/密钥服务，不进代码、不进配置文件、不进聊天记录。
3. 换 key 时先配新 key、验证通过后再 revoke 旧 key，别反过来（反过来就是一次生产事故）。

## 10. 自检与反馈

每次执行完本 skill，做一次轻量自检：

1. 脚本是否真的跑了（而不是「我觉得没问题」）？→ 没跑不算做
2. blocker 是否清零或全部列入「需人工处理」？→ 有遗漏就补
3. 联调六步是否逐项打勾？→ 打勾要有依据（截图/日志/记录表）
4. 上线检查清单六项是否全过？→ 没过的不许上线

标准冒烟用例：对插件自带的 `fixtures/` 跑脚本，确认坏 fixture 的埋点规则全命中、好 fixture 零 blocker（见仓库根 `smoke_test.py`）。

反馈渠道：以 `[QC] <一句话问题>` 为标题提交到 https://github.com/lhg-plugs/lhg-api-integration/issues，正文写清「输入 → 错误输出 → 期望输出」。规则误报/漏报请附最小复现代码。
