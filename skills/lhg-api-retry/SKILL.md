# lhg-api-retry：重试/超时/限流/熔断策略

> 目标：让 API 调用在「网络抽风、对方限流、服务抖动」时自己扛住，而不是半夜把你叫醒。
> 核心纪律：**只重试值得重试的；退避要有上限；顶着限流跑是自杀。**

## 1. 何时使用

- 封装代码写完，加健壮性 → 用本 skill
- 线上出现偶发超时/429 → 按第 3 节决策表定策略
- 批量调用（如全量同步）被限流封 key → 看第 4 节本地节流

## 2. 输入输出

- **输入**：API 限流档位（文档里的 quota 说明）+ 期望调用频率 + 失败现象
- **输出**：策略卡（超时/重试/退避/熔断/降级）+ 可复用的重试装饰器代码

## 3. 分步方法论

### 第一步：先分清「失败的种类」（决策表）

| 失败 | 能重试吗 | 为什么 |
|---|---|---|
| 网络异常、连接超时、读取超时 | ✅ | 大概率是偶发，再试一次就好 |
| HTTP 429（限流） | ✅ 但要等 | 对方明确说「你太快了」，按 `Retry-After` 等 |
| HTTP 5xx（对方服务错） | ✅ 有限次 | 对方抖动，退避重试；连续 5 次还 5xx → 熔断 |
| HTTP 400/401/403/404 | ❌ | 参数错/没权限/没这东西，重试 100 次也一样 |
| HTTP 409（冲突） | ❌ 通常 | 业务冲突，重试前先解决冲突 |

**一句话记**：`超时/网络错/429/5xx` 才重试；`4xx` 是自己的问题，先修代码。

### 第二步：超时设置（两个数，别只设一个）

- **连接超时**（connect）：10 秒 —— 连不上大概率是网络或对方挂了，别傻等
- **读取超时**（read）：30 秒 —— 对方处理慢，给够时间
- 批量/大文件场景单独放宽，不要全局设 300 秒（一个 hang 住的请求拖死整个进程）

### 第三步：重试策略（指数退避 + 抖动）

```
第 1 次失败 → 等 1s + 随机(0~0.5s) → 重试
第 2 次失败 → 等 2s + 随机(0~1s)   → 重试
第 3 次失败 → 等 4s + 随机(0~2s)   → 重试
第 4 次失败 → 放弃，抛错告警
```

- **为什么指数**：线性重试（每次等 1s）在对方雪崩时是帮倒忙，指数退避给对方喘息。
- **为什么加抖动**：100 个客户端同时重试会形成「重试风暴」，抖动把它们错开。
- **上限 3 次**：超过 3 次还失败，基本不是偶发，是真有问题，继续试只是浪费配额。

### 第四步：429 与本地节流

1. **读响应头**：`X-RateLimit-Remaining` 快见底时主动降速，别等 429。
2. **429 来了**：先看 `Retry-After` 头（秒数），按它等；没有这个头就按退避策略等。
3. **本地节流**：在客户端内部记上次请求时间，保证两次请求间隔 ≥ 配额间隔 × 1.2（留 20% 余量）。
4. **批量任务**：算好总量和配额，排期跑（如每小时 1000 次配额，900 条数据分两次跑），不要写个 for 循环一口气打完。

### 第五步：熔断与降级（线上必备）

- **熔断**：连续 5 次 5xx/超时 → 停 60 秒不再发请求（直接抛「服务熔断中」），60 秒后放 1 个试探请求，成功再恢复。
- **降级**：读接口走本地缓存（标明数据时间）；写接口进队列稍后重试，并明确告诉用户「已受理，稍后处理」。
- **告警**：熔断触发必须告警（日志/消息），不要静默 —— 静默的熔断等于把故障藏起来。

### 第六步：可复用的重试装饰器（Python 模板）

```python
import random
import time
from functools import wraps

def resilient(retries=3, base_delay=1.0, retry_on=(TimeoutError, ConnectionError)):
    """指数退避重试装饰器：只重试值得重试的异常。"""
    def deco(fn):
        @wraps(fn)
        def wrapper(*args, **kwargs):
            delay = base_delay
            for attempt in range(retries + 1):
                try:
                    return fn(*args, **kwargs)
                except retry_on as e:
                    if attempt == retries:
                        raise
                    # 429 特殊处理：优先读 Retry-After
                    wait = getattr(e, "retry_after", None) or delay
                    time.sleep(wait + random.uniform(0, wait * 0.5))
                    delay *= 2
            # 不可达
        return wrapper
    return deco

# 用法：挂在 _request 或具体接口方法上
# @resilient(retries=3, retry_on=(requests.Timeout, requests.ConnectionError))
```

**注意**：HTTP 状态码类的重试（如 429/5xx）要在 `_request` 里把状态码转成带 `retry_after` 属性的异常，再进这个装饰器 —— 状态码和异常是两套语言，中间需要一层翻译。

### 第七步：批量任务排期（算一笔账）

假设你要全量同步 10 万条数据，API 配额是每分钟 1000 次、每次请求拉 100 条：

```
总请求数 = 100000 / 100 = 1000 次
理论最快 = 1000 / 1000配额 = 1 分钟
实际排期 = 1 分钟 × 1.5（余量） ≈ 2 分钟，每批之间 sleep 0.1s
```

**排期三原则**：
1. 永远按「配额 × 0.8」规划，别按满额规划。
2. 大任务拆成多批，批之间可中断可续跑（记下上次跑到的 cursor）。
3. 跑之前先发 10 个请求探路，确认 200 且没吃 429 再全量开跑。

### 第八步：重试与幂等的关系（写接口必看）

- **读接口**（GET）：天然幂等，随便重试。
- **写接口**（POST 创建）：重试可能创建出两条数据 —— 必须先确认 API 支持幂等（`Idempotency-Key` 头或业务去重），不支持就别自动重试写接口，失败了告警人工处理。
- **更新接口**（PUT/PATCH）：一般幂等，可重试，但要确认「重试时带的是同一份数据」。

**一句话**：重试策略上线前，先问自己「这个接口重试三次，会不会造出三条脏数据」。

## 4. 反模式（不要这么干）

- ❌ `while True: try: 请求; except: continue` —— 无限重试，配额烧光、日志爆炸
- ❌ 固定间隔重试（如每次等 1 秒）—— 对方雪崩时你在火上浇油
- ❌ 不加抖动 —— 多实例同时重试形成风暴
- ❌ 重试 400 参数错误 —— 错了就是错了，先修参数
- ❌ 429 来了立即重试 —— 这是被封 key 最快的方式
- ❌ 顶着限流上限跑满 —— 留 20% 余量，对方计数方式和你想的可能不一样
- ❌ 全局 timeout 设 300 秒 —— 一个 hang 住拖死全进程

## 5. 自检与反馈

每次用完本 skill，做一次轻量自检：

1. 重试集合里有没有混入 4xx？（有就删掉）
2. 退避有没有上限？（次数上限 + 总耗时上限都要有）
3. 抖动加了吗？
4. 429 的 `Retry-After` 读了吗？
5. 批量任务算过配额排期了吗？（总量 ÷ 配额 = 最少需要几轮）
6. 熔断触发时告警通道通吗？（别等真熔断了才发现告警没配）

标准冒烟用例：给装饰器造一个「前两次超时、第三次成功」的假函数，验证重试 2 次后成功；再造「一直 400」的，验证一次都不重试直接抛错。

反馈渠道：以 `[QC] <一句话问题>` 为标题提交到 https://github.com/lhg-plugs/lhg-api-integration/issues，正文写清「输入 → 错误输出 → 期望输出」。
